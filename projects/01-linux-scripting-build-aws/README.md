# Project 1 — Linux, Bash scripting, the build process & AWS hosting

> **Domains assessed:** Linux administration · Bash scripting · Node/Vite build process · nginx · AWS (EC2, IAM, S3, CloudFront)
> **Suggested duration:** 1 week · **Team size:** 1–2 · **Prerequisite projects:** none

## Scenario

AfricAir is going live. The front-end team has handed you the repository and two sentences of documentation: *"It's a Vite app. Run `pnpm build`."*

Your job as the first DevOps engineer is to:

1. understand exactly what the build produces,
2. ship it to a Linux server with repeatable, scripted, zero-downtime deployments and one-command rollback, and
3. publish the same build to a serverless, CDN-backed hosting option on AWS.

You will compare the two approaches at the end.

## Know the application before you deploy it

| Fact | Detail |
|---|---|
| Front end | Single-page app (React + TypeScript) built to **static files**. It works on its own in "static mode", with bookings kept in the browser. |
| API (`server/`) | Optional Node.js 22 service on port **4000**, with metrics on **9464**. It holds the runtime config and the secrets, and stores bookings in PostgreSQL. Build it with `pnpm build:api` and run it with `node server/dist/index.js`. All variables are listed in `server/.env.example`. |
| Runtime | Node.js 22 LTS builds both parts. In production only the **API** runs on Node; the front end is plain files. |
| Package manager | `pnpm`, pinned in `package.json` → `packageManager`. Enable it with `corepack enable`. |
| Install | `pnpm install --frozen-lockfile` |
| Quality gates | `pnpm check` (TypeScript), `pnpm test` (Vitest unit tests) |
| Build | `pnpm build` → writes everything to `dist/` |
| End-to-end tests | `BASE_URL=http://<host> pnpm test:e2e`. Run `npx playwright install --with-deps chromium` once first. |
| Routing | Hash-based (`/#/flights?...`), so the server only ever needs to serve `/index.html` and `/assets/*`. |
| Data | `src/data/airports.json` is generated by `pnpm data:airports`. It downloads from the internet, so **never** run it during a production build. |

## Part A — Understand the build (warm-up, written answers)

Run the build locally and answer these questions in `ANSWERS.md`. Show the commands you ran.

3. Why `--frozen-lockfile`? Delete `pnpm-lock.yaml`, reinstall, and describe what changed and why that is dangerous in CI.

5. Why must `pnpm dev` **never** be used to serve production traffic? Give three reasons.
6. Total size of `dist/`, and its size gzipped (`tar czf - dist | wc -c`)?

## Part B — Ship it to a Linux server (EC2)

### B1. Provision the server

- Launch an **Ubuntu 24.04 LTS** EC2 instance (`t3.small` is enough) in a public subnet.
- **Security group:** port 22 from **your IP only**; ports 80 and 443 from anywhere.
- Attach an **IAM instance profile** with `AmazonSSMManagedInstanceCore` so you can use Session Manager.
- **Stretch:** remove port 22 entirely and work only through SSM.
- Tag everything with `Project=africair` and `Owner=<your-name>`.

### B2. `bootstrap.sh` — idempotent server setup

Write `scripts/ops/bootstrap.sh`. It must:

- start with `set -Eeuo pipefail`, trap errors and print the failing line number;
- refuse to run unless it is running as root;
- install Node.js LTS, `corepack`, `nginx`, `git`, `ufw`, `jq` and `curl`;
- create a **system user** `africair` with no login shell;
- create this layout:
  ```text
  /opt/africair/
    releases/          # one directory per deployed build
    shared/            # anything that survives releases (logs, config)
    current -> releases/<id>
  ```
- configure `ufw` to allow only OpenSSH, 80 and 443;
- be **idempotent**: a second run must change nothing and exit 0. Prove it by showing the output of two consecutive runs.

### B3. `build.sh` — a reproducible build artifact

`scripts/ops/build.sh <git-ref>` must:

1. clone or fetch the repository into a temporary build directory, then check out `<git-ref>` (a branch, tag or SHA);
2. run `pnpm install --frozen-lockfile`, `pnpm check`, `pnpm test` and `pnpm build`, **stopping on the first failure**;
3. write `dist/version.json` containing `{ "commit", "ref", "builtAt", "builtBy", "nodeVersion" }`, using `jq`, not string concatenation;
4. package the build as `africair-<shortsha>.tar.gz` plus a `.sha256` checksum file;
5. exit with **distinct exit codes**: 10 for checkout failure, 20 for install, 30 for tests, 40 for build. Document them in the script's `--help` output.

### B4. `deploy.sh` and `rollback.sh` — zero-downtime releases

`scripts/ops/deploy.sh <artifact.tar.gz>` must:

1. verify the checksum and abort if it doesn't match;
2. extract to `/opt/africair/releases/<UTC-timestamp>-<sha>/`, owned by `africair`;
3. switch `current` **atomically**. Use `ln -sfn` to a temporary link, then `mv -T`, and explain in `ANSWERS.md` why a plain `ln -sfn` is not atomic;
4. run `nginx -t` before reloading — never restart nginx;
5. `curl` `/healthz` and `/version.json`. If the commit doesn't match, **roll back automatically** and exit non-zero;
6. keep only the 5 most recent releases.

`scripts/ops/rollback.sh` switches `current` back to the previous release in one command.

### B5. nginx configuration

Write `/etc/nginx/sites-available/africair` (commit a copy to `deploy/nginx/africair.conf`):

- `root /opt/africair/current;`
- `location = /healthz` returns `200 ok` as `text/plain` and is **not** logged;
- `/assets/` gets `Cache-Control: public, max-age=31536000, immutable`;
- `/index.html` and `/version.json` get `Cache-Control: no-cache`;
- gzip enabled for JS, CSS, JSON and SVG;
- security headers: `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, and a `Content-Security-Policy` that still lets the app work. Hint: Google Fonts are loaded from `fonts.googleapis.com` and `fonts.gstatic.com`;
- an access log in **JSON format** written to `/var/log/nginx/africair.access.json`;
- a `logrotate` rule: daily, keep 14, compress.

**Stretch:** HTTPS with Let's Encrypt (`certbot --nginx`) on a domain or a free `nip.io`/`sslip.io` hostname.

### B6. Health monitoring with systemd

- Write `scripts/ops/healthcheck.sh`, plus a **systemd service and timer** (not cron) that runs it every minute.
- It logs to journald (`logger -t africair-health`).
- After **3 consecutive failures** it reloads nginx and writes a `WARNING` entry. Keep the failure count in a state file under `/var/lib/africair/`.
- Show `systemctl list-timers` and `journalctl -t africair-health --since "10 min ago"`.

### B7. Log analysis

`scripts/ops/report.sh [logfile]` prints, from the JSON access log, using `jq`, `awk`, `sort` and `uniq` only:

- the top 10 client IPs;
- request counts grouped by status class (2xx/3xx/4xx/5xx);
- the 10 most requested paths;
- requests per minute for the last hour.

Generate traffic first: run the e2e suite against your server a few times, and `curl` some 404s.

### B8. Run the API with systemd, environment files and credentials

The site is more than static files: the API in `server/` changes what users see, based on environment variables and secrets. Run it on the same server.

1. **PostgreSQL:** install it locally (`apt install postgresql`), then create a database `africair` and a role `africair_app` with a strong password. Apply the schema with `DATABASE_URL=... node server/dist/migrate.js`.
2. **Package the API:** extend `build.sh` to run `pnpm build:api` and to package `server/dist`, `server/migrations` and **production-only** dependencies in a second artifact. `deploy.sh` installs it under `/opt/africair/api/releases/<id>`, using the same atomic `current` symlink.
3. **Settings:** put the non-secret settings in `/etc/africair/api.env`, owned by `root:africair` with mode `0640`:
   ```ini
   APP_ENV=staging
   APP_VERSION=1.0.0
   ANNOUNCEMENT_TEXT=Welcome to the AfricAir staging server
   ANNOUNCEMENT_LEVEL=info
   SERVICE_FEE_USD=9
   DEFAULT_CURRENCY=KES
   ```
4. **Secrets:** store them as **files** under `/etc/africair/secrets/` (`admin_token`, `promo_codes`, `database_url`), owned by root with mode `0600`. Deliver them to the service with systemd **`LoadCredential=`**, and point the app at them with `ADMIN_TOKEN_FILE=%d/admin_token` (and the same for `PROMO_CODES_FILE` and `DATABASE_URL_FILE`). The service runs as `africair` and must **not** be able to read `/etc/africair/secrets` directly. Prove both.
5. **The `africair-api.service` unit** needs: `User=africair`, `EnvironmentFile=`, `Restart=on-failure`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, and `MemoryMax=256M`. The API handles `SIGTERM` gracefully; set `TimeoutStopSec` to more than its `SHUTDOWN_DELAY_MS` and explain why.
6. **nginx:** proxy `location /api/` to `127.0.0.1:4000`, passing `X-Forwarded-For`. Port 9464 (metrics) must **not** be reachable from outside. Prove it.
7. **Show the effect:** open `http://<ec2>/#/status`. It must show environment `staging`, storage "PostgreSQL database", and all three secrets loaded from a **file**. Then:
   - change `ANNOUNCEMENT_TEXT` and restart the service: the banner text changes;
   - set `MAINTENANCE_MODE=true`: the booking button is disabled;
   - book a flight with promo code `SAVE10`, then sign in at `/#/admin` with your admin token and find the booking;
   - rotate `admin_token` (`openssl rand -hex 24`). Does the change take effect without a restart? Explain the result. Hint: what does `LoadCredential` do at service start?

## Part C — Serverless static hosting (S3 + CloudFront)

The same `dist/` folder, without servers.

1. Create a **private** S3 bucket with Block Public Access ON, versioning and SSE-S3 encryption.
2. Create a CloudFront distribution with **Origin Access Control (OAC)**, default root object `index.html`, HTTP→HTTPS redirect, and a response-headers policy with the security headers from B5.
3. Write `scripts/ops/publish-s3.sh <dist-dir> <bucket> <distribution-id>`:
   - first `aws s3 sync` all `assets/` with `Cache-Control: public,max-age=31536000,immutable`;
   - **then** upload `index.html` and `version.json` with `no-cache`;
   - remove stale files with `--delete`, but only after the new `index.html` is live. Explain why the order matters;
   - invalidate **only** `/index.html` and `/version.json`, never `/*`. Explain why.
4. Create a **least-privilege IAM policy** for the deployer. It may only:
   - `s3:ListBucket` on the bucket;
   - `s3:PutObject` and `s3:DeleteObject` on `bucket/*`;
   - `cloudfront:CreateInvalidation` on that one distribution ARN.

   Prove it: try to list another bucket with those credentials and show the `AccessDenied`.
5. Run the full e2e suite against CloudFront: `BASE_URL=https://dxxxx.cloudfront.net pnpm test:e2e`.
6. Open `/#/status` on CloudFront: it reports **API not reachable**, and the site runs in static mode. Explain which features are missing compared with the EC2 deployment, and why S3 alone can never keep a secret.

## Acceptance checks (the instructor will run these)

```bash
# Server
curl -fsS http://<ec2>/healthz                                   # -> ok
curl -fsS http://<ec2>/version.json | jq .commit                 # -> matches the deployed SHA
curl -sI  http://<ec2>/assets/<any>.js | grep -i cache-control   # -> immutable
curl -sI  http://<ec2>/ | grep -iE 'cache-control|x-content-type|content-security'
sudo -u africair bash -c 'echo test > /etc/x'                    # -> must fail
ls -l /opt/africair/current                                      # -> symlink to a release
./scripts/ops/deploy.sh <artifact-with-wrong-checksum>; echo $?  # -> non-zero, nothing changed
./scripts/ops/rollback.sh && curl -s http://<ec2>/version.json   # -> previous commit
shellcheck scripts/ops/*.sh                                      # -> clean
curl -s http://<ec2>/api/config | jq '.appEnv, .storage, .secrets'  # staging, database, all sources "file"
curl -s -m 3 http://<ec2>:9464/metrics; echo $?                  # -> fails (not exposed)
sudo -u africair cat /etc/africair/secrets/admin_token           # -> Permission denied
systemctl show africair-api -p User,NoNewPrivileges,ProtectSystem

# CloudFront
curl -sI https://<cf>/ | grep -i x-cache
aws s3api get-public-access-block --bucket <bucket>              # -> all true
BASE_URL=https://<cf> pnpm test:e2e                              # -> all pass
```
